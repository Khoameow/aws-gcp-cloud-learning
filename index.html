Phần 1 · Services

Danh mục toàn bộ services — AWS & Google Cloud

AWS có trên 200 service và Google Cloud có 100+ products theo 22 categories chính thức — cả hai cập nhật đến 2025–2026. Chọn tab AWS hoặc Google Cloud để xem danh mục từng cloud, hoặc tab So sánh AWS ⇄ GCP để xem bảng đối chiếu tương đương kèm điểm giống/khác và gợi ý chọn bên nào. Phần 3 · Migration

Di chuyển mọi môi trường lên AWS Cloud

Theo khung AWS Prescriptive Guidance, mỗi ứng dụng được gán một trong 7 chiến lược (7R). Quy trình chuẩn gồm 3 giai đoạn: Assess (đánh giá danh mục & phụ thuộc) → Mobilize (dựng Landing Zone, tài khoản, mạng, bảo mật) → Migrate & Modernize (di chuyển theo đợt/wave và tối ưu). Đừng bỏ qua Assess và Mobilize rồi nhảy thẳng vào chuyển server — đó là nguyên nhân thất bại phổ biến nhất.

7 chiến lược di chuyển (7R)

RehostLift & shift nguyên trạng bằng MGN — nhanh nhất, ít thay đổi nhất.
RelocateChuyển ở tầng hypervisor, vd VMware → Amazon EVS / VMware Cloud on AWS.
ReplatformChuyển + tối ưu nhẹ: DB tự quản → RDS, app → container Fargate.
RefactorViết lại theo cloud-native (microservices, serverless) — tốn kém nhất, giá trị dài hạn cao nhất.
RepurchaseBỏ hệ cũ, mua SaaS thay thế (CRM, HR, email…).
RetainGiữ lại on-prem tạm thời: mới nâng cấp, ràng buộc pháp lý, chưa đáng chuyển.
RetireTắt hẳn hệ thống trùng lặp / không còn dùng — thường chiếm 10–20% danh mục.
1Assess — Đánh giá

Dùng Application Discovery Service / Migration Evaluator thu thập cấu hình server, hiệu năng, bản đồ phụ thuộc mạng. Phân loại từng app theo 7R, tính TCO so sánh on-prem vs AWS.

2Mobilize — Chuẩn bị nền

Dựng Landing Zone bằng Control Tower: Organization, SCP, IAM Identity Center, VPC nền, logging tập trung (CloudTrail, Config), ngân sách & tagging policy.

3Migrate & Modernize

Di chuyển theo wave từ ít phụ thuộc → nhiều phụ thuộc. Kiểm thử, cutover ngoài giờ cao điểm, theo dõi qua Migration Hub, sau đó hiện đại hoá dần (managed services, IaC).

Phần 4 · Sơ đồ kiến trúc

Sơ đồ chi tiết — đọc kiến trúc như Solutions Architect

Hai sơ đồ dưới đây là mẫu tham chiếu: một kiến trúc web 3-tier highly-available vẽ theo chuẩn AWS, và một sơ đồ data pipeline thực tế (kiểu sơ đồ AWS công bố cho bài toán xử lý dữ liệu xe tự hành) để bạn luyện cách đọc các sơ đồ lớn nhiều tầng.

Sơ đồ 1 — Web 3-tier Highly Available trong VPC

Public subnet chỉ chứa ALB & NAT; tầng ứng dụng và database nằm ở private subnet, trải 2 AZ. Mũi tên đứt nét là luồng dữ liệu đang chạy.

Public subnet Private — App Private — Data Route: public → IGW · private app → NAT · data → không route ra internet

Sơ đồ 2 — Data pipeline lớn kiểu AWS công bố (luyện đọc sơ đồ thật)

Sơ đồ tham chiếu do người học cung cấp: dữ liệu từ cơ sở khách hàng & IoT Greengrass → Direct Connect / IoT Core vào S3 raw → EMR kiểm tra chất lượng → Fargate/EMR làm giàu & đồng bộ → Glue Catalog, Neptune, DynamoDB, OpenSearch → QuickSight / AppSync phân tích. Hãy tập đọc theo số thứ tự 1→10: Ingest → Quality check → Enrichment → Catalog → Scene detection → Labeling → Analytics.

Phần 5 · Networking

AWS Cloud Networking — từ căn bản đến bậc thầy

Mạng là nền của mọi kiến trúc AWS. Học theo đúng thứ tự 10 chủ đề dưới đây — từ cách chia CIDR, route table, bảo mật 2 lớp, đến kiến trúc multi-VPC với Transit Gateway và hybrid cloud Direct Connect — là lộ trình của một Network Architect thực thụ.

Networking trên Google Cloud — phần song song

Khác biệt tư duy lớn nhất: VPC của GCP là tài nguyên toàn cầu (global) — subnet mới mang tính regional, một VPC phủ mọi region; còn VPC của AWS là tài nguyên regional, subnet gắn với từng AZ. Nắm chắc điểm này thì mọi khác biệt còn lại (peering, load balancer, hybrid) đều suy ra được.

Công cụ thực hành: Máy tính CIDR & chia subnet cho VPC

Nhập CIDR của VPC và số AZ — công cụ chia đều dải mạng thành các tầng Public / Private-App / Private-Data cho từng AZ, đúng quy ước thiết kế ở Phần 4. AWS dự trữ 5 IP trong mỗi subnet (network, router .1, DNS .2, dự phòng .3, broadcast).

Mẹo bậc thầy: luôn chừa khoảng CIDR trống cuối VPC cho tầng subnet tương lai (vd: subnet cho EKS, cho VPC endpoint, cho inspection). Tài liệu nền: Amazon VPC Documentation · Plan your VPC.

Security Group vs Network ACL — bảng so sánh phải thuộc lòng

Hai lớp tường lửa của VPC hoạt động khác nhau hoàn toàn. 90% lỗi “không kết nối được” khi debug đều nằm ở đây hoặc ở route table.

Phần 6 · Thiết kế dự án

Quy trình phân tích & thiết kế một dự án AWS từ A–Z

Đây là quy trình chuẩn của Solutions Architect khi nhận một bài toán thật: không bắt đầu bằng việc chọn service, mà bắt đầu bằng yêu cầu nghiệp vụ và các ràng buộc phi chức năng (NFR).

01Thu thập yêu cầu

Phỏng vấn stakeholder: nghiệp vụ, người dùng, lưu lượng hiện tại & dự báo, ngân sách, deadline, ràng buộc pháp lý (dữ liệu phải ở region nào…).

02Phân tích NFR

Định lượng: RTO/RPO, SLA uptime, p95 latency, throughput đỉnh, tăng trưởng/năm. NFR quyết định kiến trúc — không phải sở thích công nghệ.

03Thiết kế kiến trúc

Chọn service theo NFR, vẽ sơ đồ (VPC, AZ, luồng dữ liệu), quyết định các điểm đánh đổi và ghi lại thành ADR (Architecture Decision Record).

04Ước tính chi phí

Dùng AWS Pricing Calculator theo 3 kịch bản (hiện tại / tăng trưởng / đỉnh), tính cả phí ẩn: NAT Gateway, data transfer, request S3.

05Well-Architected Review

Soi lại thiết kế qua 6 trụ cột bằng AWS Well-Architected Tool, xử lý các rủi ro cao (HRI) trước khi triển khai.

06Triển khai & vận hành

IaC (Terraform/CDK) qua pipeline CI/CD, observability (CloudWatch, X-Ray), runbook, diễn tập failover & khôi phục.

Checklist trước khi chốt thiết kế (dùng cho mọi dự án)

  • Multi-AZ cho mọi thành phần production, không single point of failure
  • Private subnet cho app & data; chỉ ALB/NAT ở public subnet
  • IAM least privilege, role cho workload — không dùng access key dài hạn
  • Mã hoá at-rest (KMS) & in-transit (TLS) cho mọi dữ liệu
  • Backup & diễn tập khôi phục đúng RTO/RPO đã cam kết
  • IaC 100% — không click tay trên production
  • Tagging & ngân sách: gắn tag dự án/môi trường, cảnh báo chi phí tự động
  • Observability: log, metric, trace và alarm có người trực nhận
  • Kế hoạch cutover & rollback viết sẵn trước ngày go-live

# envs/prod/backend.tf (phía GCP)
terraform {
  backend "gcs" {
    bucket = "company-tfstate-prod"
    prefix = "prod"
  }
  required_providers {
    google = { source = "hashicorp/google", version = "~> 5.0" }
  }
}

# terraform init
# terraform fmt -check && terraform validate
# terraform plan -out=tf.plan     # đọc kỹ diff!
# terraform apply tf.plan         # chỉ apply file plan đã duyệt
# terraform plan                   # sau apply phải "No changes"

An toàn vận hành: không bao giờ sửa tay resource do Terraform quản (drift sẽ bị plan phát hiện); resource có sẵn đưa vào quản lý bằng terraform import + import block (Terraform ≥ 1.5); quét bảo mật cấu hình bằng Checkov / tfsec và policy-as-code bằng OPA (Conftest) / Sentinel (HCP Terraform) ngay trong CI; pipeline chuẩn: PR → plan tự động bằng GitHub Actions → người duyệt → apply chỉ từ nhánh main.

Đưa trang này lên GitHub Pages — static 100%GitHub Pagesへのデプロイ手順 — 完全静的サイト

01Repository đã sẵn sàng

02Đẩy file lên repo

Clone repo về máy rồi chép index.html (và thư mục assets/) vào root, hoặc tải lên bằng nút “uploading an existing file” trên GitHub:
git clone https://github.com/Khoameow/aws-gcp-cloud-learning.git
cd aws-gcp-cloud-learning
git add . && git commit -m "init" && git push origin main

03Bật GitHub Pages

Mở repo → Settings → Pages → Build and deployment → Source: Deploy from a branch → Branch: main, thư mục / (root) → Save. File chính phải là index.html nằm ở root của repo.

04Địa chỉ web chính thức

Sau 1–2 phút, trang chạy tại https://khoameow.github.io/aws-gcp-cloud-learning/. Cập nhật nội dung = sửa file rồi git push lại, Pages tự deploy lại.

Tuỳ chọn nâng cao: GitHub Actions workflow cho static site

Nếu muốn quy trình deploy có kiểm soát (hoặc repo dùng nhánh/thư mục khác), tạo file .github/workflows/pages.yml với nội dung mẫu dưới đây — workflow chính thức của GitHub cho static HTML:

# Simple workflow for deploying static content to GitHub Pages
name: Deploy static content to Pages

on:
  push:
    branches: ["main"]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: "pages"
  cancel-in-progress: false

jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Setup Pages
        uses: actions/configure-pages@v5
      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: '.'
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4

Khi dùng workflow này, ở Settings → Pages chọn Source: GitHub Actions thay vì branch. Lưu ý giữ nguyên cấu trúc: index.html ở root, ảnh trong assets/ và tham chiếu bằng đường dẫn tương đối (assets/…) để trang chạy đúng tại khoameow.github.io/aws-gcp-cloud-learning/.
